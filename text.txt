Before sign-in (during TCP/IP connection, Telnet option negotiations, and the initial TN5250 stream setup), a proxy sitting between a TN5250 client and an AS/400 (IBM i) can capture and inspect specific technical metadata and protocol negotiations defined by RFC 2877: 5250 Telnet Enhancements and standard Telnet/TN5250 framing: [1] (https://www.rfc-editor.org/info/rfc2877/)

1. Network & Transport Layer Info

• Client and Server IP Addresses & Ports: Standard TCP source/destination IPs and the Telnet/TN5250 port (typically Port 23). [1] (https://wiki.wireshark.org/TN5250)
• Connection Timestamps & State: Connection initiation, handshakes (SYN, SYN-ACK, ACK), and keep-alive intervals. [1] (https://download.gar.no/doc/ios/settings/frame_s_5250.htm)
• TLS/SSL Handshake Details: If the session is wrapped in TLS (e.g., TLS 1.2 or 1.3), the proxy can see the Server Name Indication (SNI), cipher suites negotiated, and client/server certificates (if client certificate authentication is enforced by the OS/400). [1] (https://github.com/hlandau/tn5250/blob/master/README.ssl), [2] (https://www.tn5250.com/), [3] (https://scc.its.state.nc.us/hod/en/doc/install/install.html)

2. Telnet & TN5250 Protocol Negotiations (Before Sign-On)

• Terminal Type / Model: The display model requested/negotiated by the client (e.g., IBM-3179-2 for 24x80 color or IBM-3477-FC for 27x132 color). [1] (https://www.mochasoft.dk/tn5250started.htm), [2] (https://ujs-zephyr2.alacourt.gov/pec/help_user_guide/menu_commands/communication_setup_connection_tn5250_display.htm)
• Requested Device Name (DEVNAME): The specific 5250 device/station name the client is requesting (or passing via RFC 1572/2877 environment variables like USERVAR / DEVNAME), such as a pre-assigned workstation name like DSP01. [1] (https://www.scottklement.com/tn5250/windocs.html), [2] (https://linux.die.net/man/5/tn5250rc), [3] (https://www.rfc-editor.org/info/rfc2877/)
• Code Page / CCSID: The character set and translation map negotiated between the client and the AS/400 (e.g., CCSID 37 for EBCDIC-to-ASCII mapping). [1] (https://linux.die.net/man/5/tn5250rc)
• Printer / Feature Attributes: If a printer session or specialized keyboard/display attributes are being requested alongside the display LU, those capabilities are declared during the initial telnet negotiation stream. [1] (https://www.rfc-editor.org/info/rfc2877/)

3. Authentication & Identity Artifacts (If Applicable)

• Kerberos / SSO Tickets: If the client is configured to bypass the sign-on screen using a Kerberos principal, a Kerberos service ticket is passed to the host during the TN5250/Telnet negotiation phase. A transparent proxy (or specialized gateway) can intercept or log the presence of this ticket, though the actual user identity is encapsulated inside the Kerberos blob. [1] (https://www.ibm.com/docs/en/SSEQ5Y_15.0.0/com.ibm.pcomm.doc/books/pdf/admin_guideV140.pdf)
• External Proxy Headers / JWT (in Gateway Setups): If the connection passes through an intermediate web-to-terminal or reverse-proxy gateway (such as OpenLegacy or a Telnet redirector), pre-authentication tokens like an External JWT or trusted HTTP/proxy headers may be passed to the proxy layer before the raw 5250 stream is instantiated. [1] (https://www.openlegacy.com/products/ol-terminal/help/user-management)
Note: Actual user credentials (username and password typed into the green-screen sign-on prompt) are transmitted after this phase is complete and the sign-on screen is rendered—unless clear-text auto-login parameters or pre-negotiated auto-signon mechanisms are explicitly embedded by the client configuration. [1] (https://www.rfc-editor.org/info/rfc2877/), [2] (https://www.mochasoft.dk/tn5250started.htm)
